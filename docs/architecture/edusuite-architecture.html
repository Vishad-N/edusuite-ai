System design · v1 · November 2026

EduSuite / Satyadhi Sharma Tech: backend and platform plan

The desktop app's look and screens stay as they are. This plan adds a real backend on one VPS: logins that check passwords, shared data, AI that actually runs on a server, file storage, and a signed Windows .exe that updates itself.

01Requirements and assumptions

Today every "Generate" button waits on a timer and returns a template. Logins accept anyone, and data disappears when the app restarts. The backend has to fix those three problems first.

Functional

  • Staff log in with an employee ID or email and a password that is actually checked; they log in again each day
  • Five roles: Super admin, Branch admin, Teacher, DTP/Typist, Counselor
  • Multiple institutes and branches; all data is kept separate per institute
  • Saving and reopening work from all 14 tools, plus history
  • Real AI: PPT outlines, question papers, DPPs, lesson plans, notices, YouTube metadata, doubt solving, and reading Hindi MCQs from screenshots
  • Students, fee receipts with numbers that never repeat, ID cards
  • Exports to PPTX, PDF, PNG, and WhatsApp-ready text

Non-functional

  • Starting scale: 1–20 institutes, up to 500 staff, about 150 using it at once
  • Normal screens respond in under 300 ms (p95); AI runs in the background with live progress
  • 99.5% uptime on one VPS; lose at most 24 h of data; restore within 2 h
  • Hindi (Devanagari) works correctly from start to finish
  • Installs on Windows 10/11 without admin rights and updates itself
  • AI costs can be measured and capped per institute

Constraints

  • Hosting is one VPS you control. Pick a provider with an Indian data centre (Mumbai or Bangalore) for low latency from Indore.
  • A small team (1–2 JavaScript developers), so the whole system uses one language: TypeScript
  • Keep the current React screens, Tailwind classes, translations, and the navy/amber look
  • The AI key lives only on the server, never on staff PCs

02System design map

The desktop app only talks to the server over HTTPS. Caddy is the one public entry point. Everything else runs on a private Docker network, and slow AI work goes through a queue to a separate worker process.

Amber outline = the components this plan builds or changes. Dashed = outside the VPS. Postgres, Redis and MinIO are never exposed to the internet.

Why one documents table

PPT, paper, DPP, lesson, book, notice, YouTube and doubt are all "a titled thing with structured content". Storing content as JSONB, checked by a per-type zod schema with a schema_version, means adding a new tool needs no migration. Revisit this if you ever need to search inside one type's fields.

Receipt numbering

Receipt numbers like IND-BKN/2026-27/000431 come from receipt_counters, read with SELECT … FOR UPDATE inside the same transaction that inserts the receipt. There are never gaps or duplicates. Receipts are never deleted, only cancelled with a reason, and the cancellation is written to the audit log.

07API surface

REST under /api/v1, JSON only, with an OpenAPI spec generated from the zod schemas. Every route goes through an auth guard, a permission guard and an institute-scope check.

Errors

One error shape everywhere: {code, message, details}, with Hindi and English messages chosen by Accept-Language, so the UI can show them without changes.

Pagination

Lists use cursors (?cursor=) ordered by updated_at, id, which stays stable while staff are adding records.

Idempotency

POST /fee-receipts and POST /ai/jobs accept an Idempotency-Key header, so a double click or a network retry never creates two receipts or pays for two AI runs.

08AI layer

All AI runs in the worker through one job registry. Each job type is a small file defining its input schema, prompt, output schema and post-processing step.

How a job type is defined

// packages/shared/ai/jobs/paperGenerate.ts
export const paperGenerate = defineJob({
  type: "paper_generate",
  input:  z.object({ subject, grade, topics, mcq: z.number(), short, long, lang }),
  output: QuestionPaperSchema,          // same schema the UI renders
  model:  cfg("AI_MODEL_PAPER", "claude-opus-5-5"),
  effort: "medium",
  system: PAPER_SYSTEM_PROMPT,          // stable → prompt-cached
  user:   (i) => buildPaperPrompt(i),
  after:  saveAsDocument("paper"),
});

Rules every job follows

  • Structured output: the response format is the job's JSON schema, and zod validates it again before saving
  • Streaming for long outputs (books, papers) so requests never time out
  • Refusals: check stop_reason and show the teacher a clear message instead of a broken document
  • Retries: BullMQ retries 3 times with backoff on 429/5xx; it never retries a 400
  • Prompt caching on the stable system prompt and institute style guide
  • Metering: every call writes tokens and cost to ai_usage; the API refuses new jobs once the institute's monthly quota is used up
  • Hindi first: prompts state the output language; Devanagari is checked in tests
Cost guide at the default model (Opus 5.5: $4 input / $20 output per million tokens). One PPT outline uses about 2k tokens in and 4k out, roughly $0.09. One screenshot MCQ is about 2k in and 0.5k out, roughly $0.02, so a 20-screenshot set costs about $0.40. Each job type can be moved to a cheaper model in configuration whenever you decide quality allows it.

09Security and roles

Problems in today's build that this plan removes: any unknown ID logs in, and an ID containing "super" becomes super admin; shared master passwords work on every account; passwords are stored in plain text; webSecurity: false in Electron; the AI key is kept in the PC's localStorage; all data is lost on restart.

Controls

  • Passwords hashed with argon2id. Accounts lock after 5 wrong attempts for 15 minutes. No master passwords.
  • Short-lived access JWT (15 min) plus a rotating refresh token. Reusing an old refresh token ends every session for that user.
  • Super admin can see and revoke each device session
  • Every write is checked against the user's institute and branch on the server, never trusted from the client
  • Caddy rate limits, request size limits, and type and size checks on uploads
  • Electron: webSecurity on, sandbox: true, strict CSP, preload exposes only named functions
  • Secrets live in the VPS .env (chmod 600). Only ports 80/443 are open, plus SSH by key only.
  • Audit log for logins, user changes, receipts, deletions and exports

10Windows app and installer

What staff experience

  • Download Satyadhi-Sharma-Tech-Setup-1.0.0.exe from yourdomain/download
  • Double-click. It installs per user, with no admin prompt, and adds Start menu and desktop shortcuts.
  • The first launch opens the existing login screen; the server address is built in
  • Updates download quietly and install on the next restart. There is nothing to reinstall.
  • If the internet drops, open drafts stay in IndexedDB and sync when the connection returns. AI needs to be online.

electron-builder changes

              "url": "https://updates.yourdomain/win" }],

Code signing matters for a smooth install. An unsigned .exe shows Windows SmartScreen's "Windows protected your PC" warning, which stops most staff. Buy an OV code-signing certificate, or use Microsoft's Azure Trusted Signing if your business is eligible, and sign in the CI build. Prices and eligibility change, so check them before buying.

Electron main process changes

  • Remove webSecurity: false; add sandbox: true and a CSP that only allows api. and files. on your domain
  • IPC handlers: auth:getToken/setToken (safeStorage), print:toPdf, file:saveAs, app:version, update:status
  • Load only the bundled dist/index.html in production; the localhost fallback is for development builds only
  • Single-instance lock, so a second double-click focuses the open window

14Key decisions and trade-offs

ADR-1 · Modular monolith, not microservices

One API codebase with clear modules, plus a worker process from the same code. Gain: one deploy, one database, easy debugging for a small team. Cost: modules share a process, so a bad memory leak affects all of them. Revisit when a single module needs to scale on its own (most likely AI).

ADR-2 · AI runs only on the server, through a queue

Gain: the key never leaves the VPS, you get quotas and cost tracking per institute, retries, and the UI never freezes. Cost: Redis and a worker to run, plus SSE plumbing. Calling AI from each PC was rejected because anyone could pull the key out of the app.

ADR-3 · JSONB documents table for the template tools

Gain: new tools ship without migrations, and the content shape matches the React state already in the components. Cost: the database can't enforce fields inside content; zod schemas with schema_version do that instead. Fees and questions stay as strict relational tables.

ADR-4 · Keep Electron

Gain: zero UI rewrite, printToPDF, safeStorage, and the NSIS config is already done. Cost: an installer of about 100 MB and higher memory use than Tauri. That is acceptable for office PCs.

ADR-5 · Self-hosted S3-compatible storage

Gain: everything stays on your VPS, and the app code uses the standard S3 API. Cost: disk fills with screenshots, so add a lifecycle rule that deletes raw uploads after 30 days. MinIO's community edition has changed licence and features recently, so check it at setup; Garage or SeaweedFS are drop-in alternatives.

What to revisit as you grow

  • More than about 50 institutes, or the worker saturating the CPU: move the worker to a second VPS (it only needs Redis, Postgres and storage addresses)
  • Need under 1 h data loss: turn on Postgres WAL archiving, or move to a managed Postgres
  • Slow installer downloads: put the update feed behind a CDN
  • Tenant isolation audits: add Postgres row-level security on institute_id as a second layer under the app checks
  • Parents or students as users: add a separate web portal against the same API, with its own role set
